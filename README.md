# GCP Healthcare Data Platform

This repository implements a **metadata-driven healthcare data platform on Google Cloud Platform**, designed to ingest file-based clinical data with **strict governance, schema control, and auditability**.

The platform intentionally separates **control** from **execution** to prevent schema drift, silent corruption, and operational chaos as data volume and domains scale.

> **Core principle:**  
> Control the data *before* it scales.

---

## 🎯 Platform Objectives

* Enforce **Bronze-layer governance**, not raw dumps
* Prevent schema drift and implicit mutations
* Separate **control plane** from **execution plane**
* Enable safe retries, replay, and backfills
* Maintain auditable, deterministic ingestion
* Support multi-domain growth without rewrites

This is a **platform**, not a collection of pipelines.

## 🧠 The Metadata Framework (Shared Governance)

To enforce strict separation of duties and centralized governance, **all operational metadata and data contracts live in a dedicated _Shared Governance Project_**, isolated from compute and storage workloads.

Execution environments remain stateless and replaceable.

---

### Core Principles

* **Separation of Control & Execution**  
  Metadata defines *what is allowed*. Pipelines only execute approved behavior.

* **Single Source of Truth**  
  Contracts, mappings, and audit state are authoritative and shared.

* **Multi-Domain Ready**  
  New domains onboard by registering metadata — not by changing code.

---

### Centralized Contracts

All schema and validation contracts are deployed in the **shared governance project**.

* **Pre-Dataflow Validation**
  * JSON contracts used by Cloud Functions
  * Fast rejection and schema drift detection
  * Prevents invalid data from reaching Dataflow

* **Dataflow Validation**
  * YAML ingestion contracts drive in-depth validation
  * Column order, types, nullability, and cleanup rules
  * Supports controlled schema evolution

JSON contracts optimize **speed**, YAML contracts optimize **correctness**.

---

### Unified Audit Log

The `file_ingestion_audit` table resides in the shared project’s `ops` dataset.

It provides:
* A single pane of glass for ingestion health
* Cross-domain visibility into failures
* Replay and backfill coordination

The audit table represents **durable target state**, not transient logs.

---

### End-to-End Ingestion Lifecycle

| Stage | Component | Action | Status Code |
| :--- | :--- | :--- | :--- |
| **1. Landing** | GCS | File arrives in bucket | `ARRIVED` |
| **2. Validation** | Cloud Function | File validated vs contract | `VALIDATED` / `FAILED` |
| **3. Loading** | Dataflow | Data ingested to Bronze | `LOADED_BRONZE` |
| **4. Transform** | dbt | Silver / Gold processing | `PROCESSED` |

Each status represents a **durable state transition**.

## 🧭 Orchestration

The platform is orchestrated using **Apache Airflow**, self-hosted on a Google Compute Engine (GCE) VM to maintain control with minimal overhead.

Infrastructure is provisioned using Terraform in the landing-zone project:  
https://github.com/aazad612/using-azure-devops-gcp-landing-zone

---

### Orchestration Strategy

* **Sensor-Based Pattern**
  * Airflow polls shared metadata tables
  * Files marked `VALIDATED` become eligible for processing
  * No hardcoded file paths or schedules

---

### Process Flow

1. **Bronze Loading**
   * Airflow triggers Dataflow ingestion based on metadata
2. **Transformation**
   * dbt models process data into Silver and Gold layers

This design enables **reprocessing, backfills, and selective retries** without code changes.

---

### Infrastructure Characteristics

* Airflow runs inside a **private VPC**
* Controlled egress via **Cloud NAT**
* IAM scoped primarily to metadata access
